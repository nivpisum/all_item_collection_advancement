# 把判断依据留给后来者
## AICA 物品分类的设计史、理论边界与重建契约

**整理日期：2026年10月6日。对象：Minecraft Java 1.20.1 物品分类与收集进度项目。现用分类版本 1.0.0，实现版本 1.3.0。**

本文根据项目作者与人工智能助手的讨论，以及早期树、第一代方案、用户展开的全量底稿、第二版和第二版一建议修订稿整理。文中的“作者”指项目发起者 nivpisum（旧署名 SnowyPea），“助手”指参与设计的人工智能。

这是一份设计依据与重建契约。分类树记录现在怎样放，本文保存为什么这样放。作者在建议稿之后继续亲手修改分类，形成现用正式树；这些后续修订及 1.3.0 已落实的实现契约见文末补记。

原文所述早期决定、助手建议和后来采用的方案有各自的时间背景。保留它们的来龙去脉，不表示建议当时就已逐项获得批准；现用分类以作者手工修订后的正式树为准。

## 一、这项工作真正要保存什么

AICA 的起点不是为物品寻找一套听起来像自然科学的名称，而是一个具体问题：在一个基地中，人们会把哪些东西放在一起，才能方便地取用和归还？作者将这一安排扩展为覆盖全部指定物品的分类树，并使分类阶元成为收集进度。

作者最初这样描述自己的出发点：

> “就假设我有一个游戏内基地，分成很多区域或箱子，我更愿意把哪些物品放在一起以致最方便最合理，我就会怎么划分物品的聚类。”

一个物品往往可以服务多项任务。分组还会受到材料、配方、来源、外形、习惯和界面显示的共同影响。困难不只是“某件物品应该放哪个箱子”，而是能否在大量兼用物品中维持可理解、可执行、可修订的整体秩序。

> “我还是不够满意，我感觉现版分类法是混杂的，在目的和实操等很多方面。”

十年后，物品清单、游戏机制、界面和实现语言都可能不同。因此，最值得保存的不是某个物品永远位于某条路径，而是：当时在什么目标和约束下，在什么备选方案之间，因为什么证据作出了选择；又有什么现象足以使这个选择失效。

**分类树保存结果，设计记录保存理由，反例保存理由的边界，测试保存结果与要求之间可重复的联系。** 四者缺一，后继者都可能得到一套能运行却已改变原意的系统。

本项目留下的可继承成果，是一套经过反例修整的工作方法和一组明确约束；不是已经证明存在唯一最佳答案的自然分类理论。

## 二、哪些已经决定，哪些仍然开放

作者明确作出了以下决定。它们是理解现存材料的起点，而不是由助手从最后一份文件倒推的意图。

**对象与范围。** 每个物品标识是一“种”，不再按耐久、附魔、药效、容器内容等标识内部数据细分；不同标识仍是不同种。无限门与有限门合并为合法门。指定版本的原版内置实验性玩法纳入可考虑范围，收纳袋因此进入合法门。空气保留为普通叶节点，不为它单设一个纲。合法、非法是本项目的可获取范围标签，不是现实法律评价。

**归属与阶元。** 每一种只有一个主归属。多用途冲突逐件裁决，不使用“某用途永远胜过另一用途”的全库优先级。属不再由百科共页决定，而是人工划分；其内部应保持较小的主要功能差异，原百科页面族只作为粗略尺度参照。

**语言与例外。** 名称质朴，优先使用原版已有的通称，例如铁轨科、蛋科。允许少量非常合理、但目标版本未实现的用途作为归类约定；龙蛋并入蛋科是明确实例。这一许可不等于可以任意想象功能，也不等于把设想记录为原版事实。对外分类树用中文显示。

**界面。** 最初的设想是每个高于种的实际分类节点对应一个进度。其图标等于第一个直接子节点的图标，递归到具体物品。因此，各级首项必须考虑代表性。后来的 1.3.0 界面按展示需要处理单种属、目页面和总览，具体可见节点规则见补记。

以下则属于具体设计方案，不应冒充同等强度的永久约束：七纲如何命名；冰雪是否单设亚目；蜂蜜瓶由效果用品转到活塞配套；雕刻南瓜回到南瓜科；驻地目移入建筑纲；照明科怎样合并；空气具体放在结构方块科。这些方案后来体现在作者继续亲手调整并采用的正式树中，但被采用不等于已经证明它们对所有使用场景都最优。

后继者可以重做这些选择，但应保留旧选择的理由与替代成本。遵守现存事实，不等于必须赞同现存方案。

### 各现行阶元的设计理念

早期 NG-1 说明已经把纲称为大的检索入口，目称为工作模块，科称为材料或用品套件，属按主要功能近似聚合。要理解现行阶元为什么这样分，还需要把这些名称落到使用者的工作尺度上：**工作的性质 → 一项具体工作 → 一个小工作中可能一起拿取的东西 → 功能近乎一样的相似物 → 一个物品 ID。**

**纲：工作的性质。** 纲先回答“我现在要做哪一性质的工作”。材料供给、建筑营造、工程系统、工艺处理、农牧生产、装备取用、交通出行，构成不同的大方向。同一性质下可以有多项工作；例如工艺纲中的强化、酿造、染饰、书写各有具体任务，但都围绕物品的处理和使用展开。纲让人先进入合适的工作领域，再寻找具体用品。

**目：一项具体工作。** 目回答“我在这个领域里具体要做什么”。酿造目对应配制、管理和取用药剂这项工作，可以部署为基地中的酿药室；强化目可以对应附魔、修整或锻造区域。房间是这种工作模块的一种实际布置，一个目也可以是一排箱子、几个工作台或一处操作区。划分依据是共同服务的工作，而不是现成建筑的房间数量。

**科：一个小工作中可能一次拿取的用品。** 一项工作往往还要分成几个较小的操作或准备动作。科把其中可能一起拿、一起备齐或作为一套挑选的东西集中起来。例如酿造台科将酿造台、炼药锅、玻璃瓶组成器材套件；铁轨科将四种铁轨组成铺设铁路时可能一并取用的用品；同一材系的整块、台阶、楼梯和墙，可以组成一次施工备料的小套装。因此，同科物品可以互补，并不要求功能一样。这里的“一次拿取”说明组织尺度和使用倾向，不要求每次把整科全部拿走，也不等于一科只能占一个箱子。

**属：主要功能近乎一样、功能上足够相似的物品。** 属在科内进一步回答“这些东西是否基本在做同一种事”。六种镐具有同一主要操作身份，十六色旗帜也具有近乎相同的主要功能，因此各自可以成属；材质、颜色或性能档次的变化不必拆成不同属。效率、耐久、配方等属性仍可不同，判断着眼于主要功能和使用方式。酿造台、炼药锅和玻璃瓶彼此配合，却不是同一种操作；四种铁轨也有不同的控制作用，所以不能只因同科便强并为一个属。这正是“科聚合小工作里的互补用品，属聚合功能近似物”的分界。

**种：一个物品 ID。** 种是分类中最小的身份单位，严格对应带命名空间的注册 ID。同一 ID 的药效、附魔、耐久和其他堆栈数据可以影响实际使用，但不因此产生新的种；不同 ID 则是不同种。这样，属负责表达功能相似，种负责保留明确、可对回游戏注册表的身份。

**界、门与亚目承担另外三种职责。** 物品界界定这次分类的对象全集；合法门、非法门先隔开本项目采用的获取范围。亚目则是在较大的目内组织必要的工作或材料分支：现用土石目下的石、砂土、砖、冰雪四亚目，便于在大量材料中进一步定位。亚目是辅助层级，按需要设置，不要求每个目都补齐这一层。

这些阶元描述的是从检索方向到实际操作、再到物品身份的尺度。它们允许一间功能房服务一个目，也允许不同科共用一排箱子；逻辑分类与物理仓储可以配合，而不必逐级一一对应。当前树还保留材料家族和个别用途裁决，精确成员由正式树给定，不能仅凭一句层级定义重新推算全部归属。

## 三、把事实、选择和证据分开

讨论中最容易丢失的一层信息，是一句话究竟在陈述什么。

“某物品在目标版本具有某项功能”，是**机制事实**。它需要版本对应的资料、配方或游戏复现支持。

“因为这项功能，本方案把它放在某科”，是**设计选择**。同一事实可能支持多个合理位置，选择还需要目标、使用情境和竞争理由。

“玩家在这种安排下找得更快”，是**效果判断**。它需要观察或实验，而不能由命名整齐、代码正确或解释顺畅推出。

作者报告过一条直接的使用经验：朋友们几乎记不住羽毛、燧石、爆裂紫颂果等物品属于笼统的“原料科”，作者本人也会忘记。原话是：

> “我发现实际游玩时朋友们几乎不能记得这些物品是“原料科”的，我也时有忘记。”

这是本项目真实拥有的负面证据。它支持“该类别在这组人的使用中难以预测”，不支持“所有使用者都更喜欢现在的分类”，也没有证明失败唯一来自类别名称而非界面、熟悉程度或成员构成。

作者也报告过附魔、酿造、染色房间里设置专门箱子的实际便利：

> “工作纲的染色、酿造、附魔三目，我实际是把物品放入基地里对应房间里的箱子的。这有些方便，但难以推广到其他物品。”

这支持任务模块值得保留，但不证明整座基地必须照搬房间分区。

相反，“成熟综合生存基地是默认场景”“金胡萝卜更应按食品管理”“火药主要随烟火模块”等，是设计时采用的情境假设或裁决；没有任务频率记录，不能后来改写成已经测得的玩家偏好。

后面的形式定义和数学推导，是整理设计史时补充的表达。它们不能被倒填成早期版本已经具备的理论。

## 四、一个足够重建系统的形式定义

以下记号只表达必要约束，不规定编程语言或文件格式。

设环境为 **E**，至少记录游戏版本、启用功能、允许的获取机制，以及本方案服务的玩法场景。设 **U** 为作者指定的有限物品标识清单。某标识在两个环境中相同，不意味着其功能或可获取性也不变。

分类实现是一棵**有序、有名称、有阶元的根树 T**。叶节点对应 U 中的记录；每个非根节点有且仅有一个父节点。对节点 v，令 D(v) 为其全部后代叶项的标识集合。

结构上的最低要求是：

```math
D(根)=U；\qquad D(v)=\mathop{\dot\bigcup}_{c\in 子节点(v)}D(c)。
```

点并表示互不相交的并集：父类完整收纳其子类，兄弟分支没有重复物品。每个标识只出现一次。节点标注的种数必须等于实际后代叶项数，不能把文字中的总数当作证据再去验证同一个总数。

**种是记录身份；科、属是本方案建立的分组。** 现存实现允许某个科直接列种，并不要求所有路径都有同样深度。合法门与非法门中可以出现同名的科，但它们是不同位置的节点；节点名称不是全局唯一标识。

设 f(i) 为物品 i 的唯一主归属路径。f 的输入是本项目采用的物品标识，而不是玩家此次准备怎么使用它。把蜂蜜瓶拿去饮用，不会在取物瞬间将它从原来的家族改归食物。

**唯一主归属也不等于现实中只能有一个箱子存它。** 主库存、工作台旁的周转库存和多个检索入口，是部署或界面安排；它们不应各自生成一个新的分类身份。现有方案应在不依靠重复库存的情况下也能解释位置。

事实记录仍应允许一个物品同时具有多种用途、来源和配方关系。主树是为检索与进度选择的一种组织视图，不是多用途事实的删减版。次要用途可以提供交叉检索入口，但不能在主树中悄悄复制物品。

图标则满足另一条独立的等式：

```math
图标(v)=\begin{cases}
物品图标(v),&v为叶项；\\
图标(第一个子节点(v)),&其他情况。
\end{cases}
```

因此，顺序不是无关紧要的排版。交换石头属的首项，即使没有移动任何物品，也可能改变石头科、土石目、材料纲乃至根节点的图标。分类等价、顺序等价和界面等价，应分别判断。

空气说明了记录与运行的区别：它可以是分类中的普通叶项，但其进度触发、图标渲染及是否进入生存全收集分母，仍然需要独立规定。给空气找到父节点，只解决了树的位置问题。

## 五、三条推导，解释为什么旧办法会陷入困境

### 1．交叉属性不能同时完整地成为树上分支

树上任意两个节点的叶项集合，只能互不相交，或一方包含另一方。若两个集合有交集，且各自都有对方以外的成员，它们就不能同时作为一棵单归属树中的完整类群。

这解释了早期的可再生性问题：可再生物品与某项工作用品是交叉集合。先按无限、有限分门，就会把工作模块切开。早期附魔台与其他附魔用品分处两门，正是这种选择的具体表现。

合并无限门与有限门，并非认为可再生性没有意义，而是放弃它对生存用途主树的统领地位。

这里还应留下一个没有被消除的取舍：合法、非法仍然是获取范围维度。它仍会分开跨门的用途家族。这是当前保留的范围隔离约定，不应宣称本树已做到“所有层级纯粹按用途”。未来若将非法物品改成过滤视图，可以重新评估此项取舍，但不能无声改写原范围。

### 2．全局用途优先级制造的是残余集合

若候选用途集合依次为 C₁、C₂、C₃，使用固定优先级后，实际归属集合成为：

```math
D_1=C_1，\quad D_2=C_2\setminus C_1，\quad
D_3=C_3\setminus(C_1\cup C_2)。
```

于是，“食物目”可能实际表示“没有被其他优先用途收走的食物”。这一办法能给出确定结果，却没有证明结果更便于取用。一个高优先用途再少见，也会压倒低优先用途。

逐件裁决消除了这条僵硬规则，但留下另一项责任：逐件决定必须保留理由，不能变成逐次随意决定。稳定来自可查的发布结果与解释，不来自假装所有决定由一条公式自动推出。

### 3．相似、互补、加工相连，都不能简单作传递闭包

甲与乙相似、乙与丙相似，不保证甲与丙在主要功能上足够接近。甲用于制作乙、乙用于制作丙，也不保证三者适合同类。若只要存在关系便合并，材料与配方网络很容易被一条条连接拉成大组。

因此，属需要检查整组成员的差异，而不只检查每次新加入的成员是否与其中某一个相似。材料家族也需要说明加工关系到哪里终止。

这个结论同样解释了为何“Wiki 共页”不适合作为不可拆的属：页面组织是外部文献安排，既不保证功能差异一致，也不保证其分组能嵌入用途树。游戏不变而页面拆合，不能成为本项目物品身份和主归属自动变化的理由。

## 六、我们选择优化什么，而不是假装存在无条件最优

相似物品适合放在一起，因为人们需要比较和替换；互补物品适合相邻，因为人们要完成一项任务。两者都合理，但常常竞争。

按各种材质的楼梯聚合，方便“找一种楼梯”；按同一材系的整块、楼梯、台阶和墙聚合，方便“取齐这套建筑材料”。不能只重复“按用途”而不说明服务哪种取物行为。

第一代建议采用了如下分工：大的工作模块偏重共同任务；科可以是稳定材料家族或紧密用品套件；属主要容纳主要功能、操作身份相近的变体。互补物可以同科，不能仅因互补就同属。

为描述而非假装求解这一问题，可以将评价写为：

```math
J(T)=a\,检索错误+b\,任务取用成本+c\,学习与记忆负担
+d\,节点和维护负担+e\,版本迁移成本。
```

每一项都须在声明的使用场景中测量，权重应由目标决定。这里没有已测得的系数，没有已证明的全局最优树，也不应把节点最少等同于最好。

项目尤其重视一项经常被技术实现忽略的成本：**使用者能否想到去哪里找。** 一个新类即使逻辑上能容纳全部成员，如果每次都需要回忆一串例外，也可能输给稍少统一、但位置自然可预测的方案。

任务模块也不必等于房间。房间是部署；分类描述共同工作。一个模块不需要拥有全部上游原料，酿造房不必吞下所有糖、红石和火药，制箭模块也不必接管所有木棍。

## 七、材料、器物与配套：明确局部规则

### 材系优先，不是全库材质优先

现用树将基本材料及普通建筑构件按材系集中，再分加工形态；成品工具、门、船等则先按器物身份，再分材质。

同一材系的整块、台阶、楼梯、墙可以一套取走。铁矿石、粗铁、粒、锭、块可以保留材料家族；铁镐、铁门、漏斗则各自进入成品用途。木板和木台阶仍在材料家族，木板制成船以后转入载具。

这条边界是一种使用方案，不是关于物品本质的定理。静态栅栏跟材系、栅栏门跟开闭器物，是具体裁决；将来要修改，应比较受影响的任务，而不只争论它究竟更像哪一个词。

### 取消兜底原料科，不取消材料

“多于一个用途”不构成一个有用的物品家族。取消原料科，并不意味着取消铁料、木料、羊毛与线等公共供应家族。

对缺少大材料家族的物品，第一代建议将羽毛、燧石固定到制箭用品，将爆裂紫颂果固定到紫珀材料。应保存这两个决定的不同理由：前者是专门工作配套，后者是局部加工家族，不能统称为“主要用途原则已经自动算出”。

原料—产物同类，也不要求加工可逆。蜜脾块从孤立的陈设分支改与蜜脾同科，说明“不能分解回原料”并不足以打断一个容易识别的材料家族。反过来，有直接配方也不足以让最终器物永远留在原料类。

### 配套应有边界

羽毛可以在箭科，但不能因此被称为一种箭。潜影壳可以在潜影盒科，但不在潜影盒属。科可用代表器物命名，含义是“该器物及列明配套”；属则不能无说明地从功能相似偷换成配方相关。

更不能沿配方无限吸收：箭科保留羽毛、燧石，不表示木棍必须迁来；烟火用品有火药，不表示全部纸必须迁来；附魔用品有附魔台，不表示全部钻石必须迁来。

类别名称可以简短，成员判据和转出边界不能因此省略。

## 八、植物争议：一次真正暴露标准不一致的反例

第一代建议把树苗、杜鹃花丛、下界菌放在园景，把仙人掌放在种植，又把火把花种子、瓶子草荚果随成花放在园景。作者指出了这种混乱。

> “这块好像太混乱了，或者说关于植物的几个阶元，没能完美地确定好划分标准和外延。”

问题不在于仙人掌不能吃，而在于当时交替使用了外形、生产用途和最终产物三个判据，却没有说明为何在不同物品上切换。

修正后的方向是：**判断具体物品当前被管理的角色，不让整种植物或整条生命史继承一个位置。** 树苗、用于育树的杜鹃花丛和用于培育大型菌体的菌类进入种植；树叶、根形材料进入园景；取得的木材进入材料。火把花种子、瓶子草荚果与收获后的成花分开管理。

“种苗”在这里是生产投入角色，不是严格的植物发育阶段名。能作为小景观摆放，不足以自动排除种苗身份；有生长和繁殖能力，也不足以让所有景材都进入种植。

同时，一个标识兼任食物、繁殖投入和景材时，仍需单项裁决。已有方案把某些可种植食品保留在食物目，取去播种时仍从同一位置拿取。身份粒度既然不再细分，就不能靠本次用途变化偷偷创造多个种。

第二版一又将若干小科合成种苗科，但保留小麦种子与小麦同科、南瓜种子与南瓜同科。这是“已有稳定小家族优先保留”的局部安排。必须坦率记录：**这一种苗科不是所有种苗的逻辑全集，而是方案中集中管理的一组种植投入。** 它是否再次产生残余类别的记忆问题，尚待检验。

可复用的成果是角色分离方法与反例；当前种苗科的全部边界，还不是已经被实验确立的最终答案。

## 九、改判应连同被放弃的理由一起保存

若只保存最后路径，后来者会把尚有竞争关系的选择误当成物品固有属性。第二版一的几个改判，尤其值得完整保留。

作者的追问说明了这种纠结：

> “蜂蜜瓶该跟蜂蜜块还是奶桶放一起呢，真让人纠结。”

> “雕刻南瓜的功能是否足够强和显著才放入养殖目而非无论来源和去向上都极合适的种植目南瓜科？”

**蜂蜜瓶。** 先按效果用品与奶桶相邻，后按材料转换关系与蜂蜜块相邻，并作为活塞材料配套。被放弃方案的理由并未消失：效果使用和食品使用仍是竞争入口。最后位置应接受未来取用测试，而不是被升格为“可转换物一律同类”。

**蜜脾块。** 从单独陈设改与蜜脾同科，修补的是可识别材料家族被孤立的问题。这并未恢复“所有蜜蜂产物同类”；蜂巢、蜜脾和蜂蜜仍服务不同模块。

**雕纹书架。** 从通用仓储转入书写目的书科，与讲台相邻。取舍在于专用服务对象和通用容器身份之间，不在于“它究竟是不是容器”。普通书架仍留在附魔配套，是另一项单独裁决。

**雕刻南瓜。** 先因生物生成用途独立成科，后回南瓜科。改判承认一项显著功能不必独占分类入口；已有家族的可预测性可以更重要。南瓜灯、南瓜派并未一并迁回，材料链仍有成品边界。

**避雷针。** 从红石探测元件转为驻地防护配套，并促使整个驻地目由出行分支移入建筑纲。这个案例说明，局部放置不协调有时暴露的是父级模块位置的问题，不能只在两只箱子之间反复搬动同一物品。

**冰雪与岩浆块。** 没有因为它们是亚目之外的剩余项，就捆成一个“冷热”组。建议只组冰雪亚目，岩浆块回石材。结构整齐是收益，但不应单独创造语义牵强的类。

上述是有记录的设计修正，不是已获总体优胜证据的实验结论。这些改判已体现在现用正式树中；建议稿之后作者继续作出的调整另列于补记。

## 十、命名、阶元和首项，本来就是系统行为

作者偏好铁轨科、蛋科，而不是为简单家族创造抽象名称。其价值不只在文风：熟悉名称能让使用者直接预测内容，也能减少后继维护者重建术语的成本。

但代表器物命名有边界。火把科若容纳灯笼、蜡烛等，必须说明是照明器物家族；名字不能成为任意扩张成员的许可证。效果用品取名药水科，也须记录它包含列明的非药水成员。维护者需要同时保存**公开短名、范围定义和具体成员**。

中文显示名与物品身份也应分开。历史输出为了只用中文，给部分唱片采用中文辨识别名，将某些英文显示名改成中文。它们不是新物品，也不一定是官方译名。若仅保存中文树而丢掉原标识映射，十年后的译名变化可能使物品无法可靠对回。正式分类树因此同时保存中文显示名和物品 ID，正文不再重复列出全量标识。作者后来还将“炸药”“炸药矿车”恢复为 TNT、TNT 矿车，显示名以现用树为准。

每多一个实际阶元，就多一个分类节点、多一个需要解释的概念和一项维护责任；映射到进度界面时，还可能增加可见目标。第二版撤掉色系、唱片作者、陶片题材等低收益分组；随后又发现照明中“一个科只套一个属”的重复包装过多，第二版一继续合并。这段往返值得保留：**细分过多与合并过粗都可能失败，节点数量不是单向越少越好。**

如果父节点只有一个子类，两者的叶项集合相同。若又使用相同的完成规则，它们的完成结果也相同。可以为阶元表达保留这种重复，但应说明它提供了什么额外信息，不能只为排齐层级复制进度。

反过来，某件物品有足够独立的检索身份时，保留单种科并不自动错误；把甘蔗、可可豆、仙人掌、海带统收“其他作物”，可能只是重新制造原料科。

首项还会限制图标选择。鸡蛋代表蛋科，比让龙蛋代表更符合本方案的普通代表偏好；石头而非稀有特例代表材料；钻石镐是工具分支选定的视觉代表。这些是代表性判断，不是稀有度或性能排序。

图标递归等式可以自动验证，但“是否最具代表性”不能仅靠等式验证。若父节点的理想代表与首子类的理想代表冲突，需要重排或承认取舍；不能声称递归正确就已经完成了视觉设计。

## 十一、怎样判断另一个实现是否正确

“正确”至少分为三个问题，测试不能互相冒名。

**第一，结构有效。** 对指定全集，每个物品身份恰好出现一次；树有根、无环、父子关系明确；计数来自实际后代；节点顺序可恢复；图标表由主树递归生成；不存在来源不明的显示名。违反这些条件，是实现错误。

**第二，忠实复现。** 声称复现分类 1.0.0，就要保留作者正式树的成员、父子关系、必要名称、顺序与图标。把蜂蜜瓶放回效果用品，即使理由不错，也不是原样复现。反过来，未来一个明确声明重新设计的版本，不应只因它没有保留蜂蜜瓶的旧位置而被判不合格。

**第三，使用适当。** 结构正确、快照一致，仍不能证明它比另一个方案好用。检索、归还、任务取齐、长期记忆和升级稳定性，需要独立证据。

启用搜索的界面与纯树导航也应分开评价：搜索可以掩盖类别不易预测的问题，却不一定改善归还或理解。

因此，测试必须标注效力。某一物品的精确路径，可以是历史快照回归用例；“每个标识唯一出现”则是跨实现的不变量。若把前者全部升级成永久规则，测试集就会把当前树冻结成传统；若两者都允许新版本随意重写，测试又失去约束作用。

## 十二、进度语义不能靠分类树猜出来

“每个上位节点是一个进度”只规定节点对应，不自动规定什么时候点亮。

设玩家已经记录的物品集合为 C，某节点要求纳入收集的范围为 A(v)。需要明确区分发现与集齐两种语义：

```math
已发现(v)\iff C\cap A(v)\ne\varnothing；
```

```math
已集齐(v)\iff A(v)\subseteq C。
```

两者必须区分；它们也都不同于“玩家当前背包同时持有全部物品”。物品消耗后是否保留进度、丢失或死亡是否影响记录、分类升级后怎样迁移，不能从节点名称推出。

同样，A(v) 未必等于 D(v)。现用 1.3.0 排除非法门与空气，物品界的收集范围是合法门的 1146 种；收纳袋通过启用原版内置配方纳入。一般而言，若过滤后 A(v) 为空，数学上的全集包含会自动成立，但这未必是期望的游戏显示行为；必须规定隐藏、停用或其他处理。

1.3.0 已将两种语义分别落实：隐藏条件发现分支，可见目标要求所有成员已被记录。记录可以在不同时间积累，不要求同时持有全部物品；已有物品条件和日期的升级处理见补记。

后继实现可以改语言、换界面，但必须明确并保持这一合同，再声称进度行为与某个版本兼容。

## 十三、没有消失的取舍

现用方案仍保留以下取舍。它们说明哪些收益没有被一个整齐的树形结构自动解决。

**功能距离尚未量化。** “属内差异很小”仍需例证与边界判断，不能保证不同维护者独立分属时完全一致。

**若干集合仍有残余性质。** 种苗科收一部分种苗，另一些留在小麦、南瓜等家族；这种安排可能便利，也可能重新制造记忆负担。

**一些配套牵引仍有风险。** 蜂蜜瓶进入活塞科后，按饮食或效果寻找它的人可能更不方便；蜜脾块进入染饰目、普通书架留在附魔等，也保留了有待实测的竞争入口。

**代表性没有受众测试。** 递归图标可以算对，所选图标是否让陌生使用者理解相应大类仍未知。

**标识粒度有意丢弃细节。** 这是作者为控制复杂度作出的取舍，不是断言同一标识的所有实例在用途上完全相同。新增细分必须作为范围改变，而非暗改现有种的含义。

## 十四、给重写者的最小交付合同

未来的人或人工智能不必维持当前七纲、编程语言、文件结构或每个物品的位置，但要使成果仍然可继承，应当保留下列相互连接的信息；它们可以写在同一篇文档中，不要求拆成一套过程文件。

**对象清单与环境。** 保留稳定物品身份、中文显示映射、版本与开关、特殊记录及收集范围。只有名称、没有身份的树，不足以抵抗译名变化。

**有序树快照。** 保存成员、父子关系、阶元、顺序和图标生成规则；程序生成的图标表、索引、分卷必须能从同一来源重建。

**决策记录。** 对重要争议写明候选位置、支持各候选的事实、最终取舍、牺牲的收益、决定者与确认状态、适用环境，以及什么变化会触发重审。没有被采用的强理由尤其要保存。

**测试与真实结果。** 区分通用不变量、历史快照回归、机制复现和使用效果。说明检查针对什么要求、结果能支持什么结论。静态通过不能填写到“好用”一栏。

**迁移与废弃记录。** 改名、调序、迁移、合并、拆分和范围变更不是同一种操作。应保存旧新身份映射和图标变更；涉及收集完成时，还需说明旧玩家状态如何迁移。路径会变，不能永远拿中文路径兼任实体身份。

**出处与未决问题。** 区分作者明确要求、助手建议、游戏事实、推测用途和实验结果。不把提问写成批准，不把合理设想写成原版机制，也不把实现通过写成用户体验已经获胜。

对一次重要归属修改，最低限度的一条完整记录应该能够回答：

> 谁在什么版本中，面对哪几个候选，因为哪条证据或约束作了什么选择；哪个旧选择被替代，哪一项收益被牺牲；用什么测试能证明实现忠实，又用什么观察能推翻这项选择。

两个实现可以同时合理，但使用相同类名不保证具有相同外延。公开分支应标明版本、环境、相对于哪份基线改变了什么；名称沿用不能冒充语义兼容。领域的秩序来自可追溯的继承和可比较的差异，而不是禁止出现另一棵树。

这样，新的实现可以不同，却不必失忆。

## 结语

AICA 的讨论没有找到一条能不带选择地分尽所有物品的定律。它明确了哪些问题可以严格判定，哪些取舍需要声明，哪些“方便”必须接受使用检验；也留下了几次看似整齐的分类如何被实际反例推翻。

有序不等于以后不许改动。有序是：每次改动都能指出继承了什么、改变了什么、为何改变，以及凭什么判断改得更好。

**应该传给后来者的，不是“这些物品只能这样放”，而是“我们遇到过这些冲突、试过这些办法；这是留下的依据，也是允许你推翻我们的条件”。**

非法门含管理、材料、建筑、农牧、交通五纲。管理纲面向命令、结构与编辑等世界管理工作；其余同名纲沿用相应工作性质，但这些是不同节点。空气是非法门下的普通种，位置为 `管理纲／结构目／结构方块科／空气`，不另设空气纲，也不作为上位节点图标。

游戏版本、分类版本和程序版本各自独立。1.3.0 的界面与进度改进沿用分类 1.0.0，不代表分类树也升级成了 1.3.0。

### 建议稿之后的手工修订

原设计文献的最后一棵建议树，与现用正式树不是同一份结果。后续修订保留 1255 个物品 ID 的全集及两门范围，具体包括以下归属变化：

| 物品 | 原建议位置 | 现用正式位置 |
|---|---|---|
| 蜘蛛网 `minecraft:cobweb` | 合法门／工程纲／红石目／蜘蛛网科 | 合法门／工艺纲／酿造目／药材科 |
| 紫颂植株 `minecraft:chorus_plant` | 非法门／农牧纲／种植目／紫颂科 | 非法门／农牧纲／种植目／种苗科 |

原独立蜘蛛网科随归属调整撤去。这些是作者的收纳分类约定，不应从“药材科”一名反推每个成员都直接参与原版酿造配方，也不应替作者补造未记录的改判理由。

名称修订为：`石材亚目 → 石亚目`、`土砂亚目 → 砂土亚目`、`装饰材料目 → 饰面目`、`果蔬科 → 蔬果科`、`点火科 → 打火科`、`虫蚀石料属 → 虫蚀属`；原建议中的“炸药”“炸药矿车”恢复为 **TNT、TNT 矿车**。这些显示名变化不产生新物品 ID。

作者还调整了同层顺序，例如建筑纲的驻地目排到门目之后；石亚目、矿物目、园景目及若干用品科重新排序；镐、斧、锹、锄、剑中的金制品排在木制品之前。**复现顺序与图标时必须读取正式树，不能沿用建议稿的树序或另附图标表。**

## 补记二、1.3.0 的实现契约与接续入口

### 生存收集进度的确定规则

1.3.0 使用 **27 个目页面加一个合法层级总览，共 28 页、721 个可见进度**。总览含界、合法门、七纲和 27 目，共 36 个节点；非法门不进入生存进度。属作为末端分类目标，其下物品保存为收集条件；单种属展示为种，科下直接列出的种也可见。所以“树里每个上位节点都必须成为一个可见进度”不是现用界面的规则。

**发现与完成分开。** 任意成员的记录用于隐藏的发现条件，只负责显露分支；每个可见分类目标均要求全部成员已被记录。物品分别获得即可，不必同时持有，使用或丢失物品不自动清除记录。附魔等级、药效等堆栈变体不增加种数。物品界的完成范围是合法门的 1146 种，而不是分类全集的 1255 种。

界、门、纲、目及四个亚目使用 Challenge，科使用 Goal，属或种使用 Task。全部进度无经验、物品、配方或函数奖励。正常收集保留原版弹窗与聊天广播；目页面的镜像根不重复通知。

旧 `all_item` 与 AICA 1.0.0 的物品条件按玩家一次性导入。已有条件日期保留，新补条件使用导入日期；不能把旧整类的完成状态直接当成其每个物品都已取得。ZIP 与 JAR 使用同一游戏数据和世界记录，切换形式仍保留收集状态；同一世界只启用一种形式。

### Forge 创造栏与浏览的确定规则

材料纲的土石、木材、矿物、饰面四目各设一页，再加其余六纲和非法门，共 **11 个 AICA 标签页**。至少三种物品的属可折叠，一种、两种属平铺；这是浏览规则，与进度的完成条件不同。

附魔书、药水、药箭、谜之炖菜等原生变体保留完整物品堆栈与 NBT，并随当前功能和管理员权限更新。白色旗帜和不祥旗帜位于已有 16 色旗帜属的同一个折叠格；额外堆栈不增加分类种数。空气为空 ItemStack，因此创造栏实际展示 1254 个物品 ID。

快捷栏、搜索和生存物品栏保留，其他模组标签页可继续访问。进度页按分类顺序排列，新节点出现、切页和关闭重开后保持已浏览的视野。原版界面及 Better Advancements 的适配属于界面层，不应反向改写分类。

### 稳定身份与源码入口

现用 Freeplane 节点 ID 是独立身份，改名或移动时应尽量保留，不每次重新生成。程序把节点 ID 的 UTF-8 字符串做 SHA-1，取十六进制前 16 位为键；分类进度通常使用 `aica:node/<键>`，目页面根使用 `aica:page/<键>`。这些资源身份参与旧记录迁移，不用中文名或路径替代。

公开实现位于 [AICA 仓库](https://github.com/nivpisum/all_item_collection_advancement)，版本基线见 [v1.3.0 源码](https://github.com/nivpisum/all_item_collection_advancement/tree/v1.3.0)。继续此工作时，按职责读取：

| 文件或目录 | 职责 |
|---|---|
| `data/aica_item_1.20.1_1.0.0.mm` | 唯一正式分类源 |
| `data/registry_1_20_1.json` | 目标物品 ID 全集 |
| `tool/classification.py` | 分类读取、身份与图标规则 |
| `tool/build.py`、`src/main/` | 进度生成、创造栏与界面实现 |
| `data/catalog.json`、`tool/legacy.py` | 旧记录映射与迁移，不决定当前分类 |
| `reference/guide.md`、`LICENSE`、`NOTICE.md` | 使用方法、兼容目标与权利范围 |

Forge 版目标为 **Minecraft 1.20.1／Forge 47.4.23／Java 17**；客户端另装 **MoreCreativeTabs 1.2.1** 和 **Inventory Item Groups 1.5.1-forge+1.20**。Cloth Config 可选，Better Advancements 0.6.0.73 为可选集成。Python 3.11+ 的 `python tool/build.py` 从正式树生成 ZIP 与 JAR，不反向覆盖分类源。
