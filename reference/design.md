# AICA 物品分类：设计思想与重建契约

适用范围：Minecraft Java 1.20.1；分类版本 1.0.0；实现版本 1.3.0。整理日期：2026 年 10 月 6 日。

AICA（All Item Collection Advancement，全物品收集进度）由 nivpisum（旧署名 SnowyPea）发起，在作者与 AI 的讨论中形成。它首先服务于基地中的物品取用、归还和成套备料，再把分类用于生存收集进度与创造栏浏览。界、门、纲、目、科、属、种是组织层级的名称，不表示这是一套自然科学分类。

**设计建议交付之后，作者又手工修改了分类，形成现在使用的正式树。** 原设计文献未掌握这一步；本文补入这些修订，并以正式树和 1.3.0 的实际实现为准。早期建议不能覆盖作者后来的决定。

## 1. 现用结果与权威来源

唯一正式分类源是 [`data/aica_item_1.20.1_1.0.0.mm`](https://github.com/nivpisum/all_item_collection_advancement/blob/v1.3.0/data/aica_item_1.20.1_1.0.0.mm)。它保存成员、父子关系、顺序、中文显示名、物品 ID 和节点 ID。本文解释设计与实现边界；精确复现时应读取这棵树，不从例子或旧建议稿重新猜树。

分类共有 **1656 个节点、1255 个物品 ID**：1255 个种节点和 401 个上位节点（含根）；合法门 1146 种，非法门 109 种。两门是本项目的获取范围标签。合法门包含原版内置实验性收纳袋；1.3.0 启用其 1.20.1 原配方。非法门保留其余登记物品，供分类与创造栏使用，不计入生存收集进度。

合法门的七纲及其目按下表顺序排列：

| 纲 | 种数 | 目，按现用顺序 |
|---|---:|---|
| 材料纲 | 487 | 土石、木材、矿物、饰面 |
| 建筑纲 | 228 | 照明、园景、门、驻地、陈设、音乐 |
| 工程纲 | 89 | 红石、仓储、加工 |
| 工艺纲 | 120 | 强化、酿造、染饰、书写 |
| 农牧纲 | 84 | 种植、养殖、食物 |
| 装备纲 | 82 | 工具、防具、武器 |
| 交通纲 | 56 | 载具、飞行、导航、通行 |

非法门含管理、材料、建筑、农牧、交通五纲。它可以与合法门出现同名类群，但这些是不同节点。空气是非法门下的普通种，位置为 `管理纲／结构目／结构方块科／空气`，不另设空气纲，也不作为上位节点图标。

游戏版本、分类版本和程序版本各自独立。1.3.0 的界面与进度改进沿用分类 1.0.0，不代表分类树也升级成了 1.3.0。

## 2. 分类方法及其边界

**一个物品 ID 是一种，一个种只有一个主归属。** 身份使用带命名空间的注册 ID，例如 `minecraft:honey_bottle`。耐久、附魔等级、药效、旗帜图案、容器内容等堆栈数据不再分种；不同 ID 仍是不同种。中文名是显示层，不用于判断身份。

主归属是稳定的收纳位置。蜂蜜瓶拿来饮用时，不临时变成另一类；工作站旁的周转库存、搜索别名或用途筛选也不生成新的分类身份。物品的多种用途仍然成立，主树只选择一个主要管理入口。

**多用途冲突逐件裁决。** 不设“食物永远优先于材料”等全库规则。固定优先级会让后面的类别成为前面挑剩的集合，名称与成员越来越难对应。早期笼统的“原料科”让作者和朋友难以记住羽毛、燧石、爆裂紫颂果的位置；因此改用可识别的家族和工作配套。取消兜底类别，不意味着取消铁料、木料等公共材料家族。

**不同层级承担不同工作。** 纲提供大的检索方向，目组织工作模块，科容纳稳定的材料家族或紧密用品套件，属容纳主要功能、操作身份相近的变体。互补用品可以同科，不因互补就同属。属由本项目人工划分，百科共页只作参考；百科页面拆合不会自动改变分类。

**材料局部按材系，成品按器物身份。** 普通建筑材料先聚合同一材系，再区分整块、台阶、楼梯、墙等形态，便于一次取齐一套材料。镐、门、船等成品先按器物身份，再分材质。铁矿石、粗铁、粒、锭、块可以同科，铁镐和铁门不因此留在铁科。木板、木台阶留在材料家族，木船进入载具。

配方、共同来源和相似性都不能无限扩张类群。甲能制成乙、乙能制成丙，不表示三者应同科；甲似乙、乙似丙，也不保证整组足够相近。箭科的羽毛和燧石是配套，不是箭；它们进入箭科，不要求所有木棍也迁来。科可以用代表器物命名，但必须由具体成员和边界解释这个短名。

**植物按具体物品当前的管理角色判断。** 育树、育菌的投入可进入种植，叶片、根形景材进入园景，收获木材进入材料。种子与成花不因属于同一种植物就必须同类。“种苗科”是一组集中管理的种植投入，不是全部种苗的逻辑全集：小麦种子、南瓜种子仍随各自稳定家族。一个标识兼任食物与播种投入时，仍只保留一个归属。

**名称质朴，层级按需要设置。** 使用熟悉的“铁轨科”“蛋科”等名称，不为整齐而堆叠色系、作者、题材等低收益层级，也不强迫每个科下面都设置属。可以由科直接挂种；单种科也可以有独立检索价值。少数分类约定可参考合理但目标版本未实现的用途，例如龙蛋归蛋科；这不表示 1.20.1 已实现龙蛋孵化。

早期“无限门／有限门”被合为合法门，是为了避免可再生性先把用途家族切开。现用树仍先区分合法与非法，所以并非每层都只按用途。整体目标是位置容易预测、成套取用方便、修改成本可控；这些取舍不构成唯一最优分类的证明。

## 3. 已采用的难例与取舍

以下案例保留设计理由和适用边界，准确成员仍以正式树为准。

| 物品或家族 | 现用归属与理由 | 边界 |
|---|---|---|
| 蜂蜜瓶、蜂蜜块 | 工程纲／红石目／活塞科；保留材料转换和活塞配套的联系 | 蜂蜜瓶的食品、解毒用途仍成立，不推出“可转换物一律同类” |
| 蜜脾、蜜脾块 | 工艺纲／染饰目／蜜脾科；保留容易识别的材料家族 | 加工不可逆不足以拆科；也不要求所有蜜蜂产物归在一起 |
| 雕纹书架 | 工艺纲／书写目／书科；按专门服务的书写用品管理 | 普通书架仍在强化目／附魔科，通用容器身份不是唯一判据 |
| 雕刻南瓜 | 农牧纲／种植目／南瓜科；保留已有小家族的可预测性 | 生成生物等显著用途不必独占入口；南瓜灯在照明，南瓜派在食物 |
| 避雷针 | 建筑纲／驻地目／避雷针科；作为驻地防护配套 | 局部位置不协调时，要检查父级模块；不沿铜配方迁回材料 |
| 岩浆块与冰雪 | 岩浆块在石亚目；冰雪组成冰雪亚目 | 不为装下剩余成员而造一个牵强的“冷热”或“冰火”类 |
| 羽毛、燧石与爆裂紫颂果 | 前两者在箭科，后者在紫珀科 | 前者是工作配套，后者是加工家族，不用一条“主要用途”口号抹平理由 |

这些位置是发布的设计选择。机制事实、分类选择和“比其他安排更好用”的判断应分开：配方与代码能够确定前两者的部分条件，不能据此宣称已证明所有玩家都找得更快。

## 4. 建议稿之后的作者手工修订

原设计文献的最后一棵建议树，与现用正式树不是同一份结果。后续修订保留 1255 个物品 ID 的全集及两门范围，具体包括以下归属变化：

| 物品 | 原建议位置 | 现用正式位置 |
|---|---|---|
| 蜘蛛网 `minecraft:cobweb` | 合法门／工程纲／红石目／蜘蛛网科 | 合法门／工艺纲／酿造目／药材科 |
| 紫颂植株 `minecraft:chorus_plant` | 非法门／农牧纲／种植目／紫颂科 | 非法门／农牧纲／种植目／种苗科 |

原独立蜘蛛网科随归属调整撤去。这些是作者的收纳分类约定，不应从“药材科”一名反推每个成员都直接参与原版酿造配方，也不应替作者补造未记录的改判理由。

名称修订为：`石材亚目 → 石亚目`、`土砂亚目 → 砂土亚目`、`装饰材料目 → 饰面目`、`果蔬科 → 蔬果科`、`点火科 → 打火科`、`虫蚀石料属 → 虫蚀属`；原建议中的“炸药”“炸药矿车”恢复为 **TNT、TNT 矿车**。这些显示名变化不产生新物品 ID。

作者还调整了同层顺序，例如建筑纲的驻地目排到门目之后；石亚目、矿物目、园景目及若干用品科重新排序；镐、斧、锹、锄、剑中的金制品排在木制品之前。**复现顺序与图标时必须读取正式树，不能沿用建议稿的树序或另附图标表。**

## 5. 分类数据的重建契约

重写语言、换编辑器或移植界面时，应保留以下含义：

1. 分类是一棵有根、有序、带名称和阶元的树，每个非根节点只有一个父节点。每个目标物品 ID 恰好出现一次；父节点的成员是全部子节点成员的不相交并集。种数由实际后代计算。
2. 保存物品 ID、节点 ID、父子关系、兄弟顺序、阶元和显示名。不能只保存中文路径；译名会变，同名类群也可能出现在两门。现用 Freeplane 节点 ID 是独立身份，改名或移动时应尽量保留，不能每次重新生成。
3. 图标递归取第一个直接子节点的图标，直到一个种；等价于取该节点树序中的第一个后代物品。顺序因此影响界面。空气保留为叶项，但不能成为任何上位节点的首个后代。
4. 允许不同路径深度不同，不补造空层级、重复身份或“其他”类来凑齐格式。分组减少到多少不是独立目标；既要避免重复包装，也要保留有用的检索入口。
5. 复现分类 1.0.0 应保留这棵正式树。重新设计可以改变成员与层级，但应明确版本、说明影响和迁移办法；一个新选择理由充分，也不等于它仍是旧分类的原样复现。

现用程序把节点 ID 的 UTF-8 字符串做 SHA-1，取十六进制前 16 位为键；分类进度通常使用 `aica:node/<键>`，目页面根使用 `aica:page/<键>`。这些资源身份参与旧记录迁移，应按现有实现保持兼容，不用中文名或路径替代。

## 6. 同一棵树的两种游戏应用

### 生存收集进度

1.3.0 使用 **27 个目页面加一个合法层级总览，共 28 页、721 个可见进度**。总览含界、合法门、七纲和 27 目，共 36 个节点；非法门不进入生存进度。属作为末端分类目标，其下物品保存为收集条件；单种属展示为种，科下直接列出的种也可见。所以“树里每个上位节点都必须成为一个可见进度”不是现用界面的规则。

**发现与完成分开。** 任意成员的记录用于隐藏的发现条件，只负责显露分支；每个可见分类目标均要求全部成员已被记录。物品分别获得即可，不必同时持有，使用或丢失物品不自动清除记录。附魔等级、药效等堆栈变体不增加种数。物品界的完成范围是合法门的 1146 种，而不是分类全集的 1255 种。

界、门、纲、目及四个亚目使用 Challenge，科使用 Goal，属或种使用 Task。全部进度无经验、物品、配方或函数奖励。正常收集保留原版弹窗与聊天广播；目页面的镜像根不重复通知。

旧 `all_item` 与 AICA 1.0.0 的物品条件按玩家一次性导入。已有条件日期保留，新补条件使用导入日期；不能把旧整类的完成状态直接当成其每个物品都已取得。ZIP 与 JAR 使用同一游戏数据和世界记录，切换形式仍保留收集状态；同一世界只启用一种形式。

### Forge 创造栏与浏览

材料纲的土石、木材、矿物、饰面四目各设一页，再加其余六纲和非法门，共 **11 个 AICA 标签页**。至少三种物品的属可折叠，一种、两种属平铺；这是浏览规则，与进度的完成条件不同。

附魔书、药水、药箭、谜之炖菜等原生变体保留完整物品堆栈与 NBT，并随当前功能和管理员权限更新。白色旗帜和不祥旗帜位于已有 16 色旗帜属的同一个折叠格；额外堆栈不增加分类种数。空气为空 ItemStack，因此创造栏实际展示 1254 个物品 ID。

快捷栏、搜索和生存物品栏保留，其他模组标签页可继续访问。进度页按分类顺序排列，新节点出现、切页和关闭重开后保持已浏览的视野。原版界面及 Better Advancements 的适配属于界面层，不应反向改写分类。

## 7. 接续开发与开放使用

公开实现位于 [AICA 仓库](https://github.com/nivpisum/all_item_collection_advancement)，版本基线见 [v1.3.0 源码](https://github.com/nivpisum/all_item_collection_advancement/tree/v1.3.0)。继续此工作时，按职责读取：

| 文件或目录 | 职责 |
|---|---|
| `data/aica_item_1.20.1_1.0.0.mm` | 唯一正式分类源 |
| `data/registry_1_20_1.json` | 目标物品 ID 全集 |
| `tool/classification.py` | 分类读取、身份与图标规则 |
| `tool/build.py`、`src/main/` | 进度生成、创造栏与界面实现 |
| `data/catalog.json`、`tool/legacy.py` | 旧记录映射与迁移，不决定当前分类 |
| `reference/guide.md`、`LICENSE`、`NOTICE.md` | 使用方法、兼容目标与权利范围 |

Forge 版目标为 **Minecraft 1.20.1／Forge 47.4.23／Java 17**；客户端另装 **MoreCreativeTabs 1.2.1** 和 **Inventory Item Groups 1.5.1-forge+1.20**。Cloth Config 可选，Better Advancements 0.6.0.73 为可选集成。Python 3.11+ 的 `python tool/build.py` 从正式树生成 ZIP 与 JAR，不反向覆盖分类源。

新增物品或移植版本时，先确定版本、功能开关和获取范围，再逐件决定主归属；类群调整同时考虑成员、顺序、图标、可见目标和旧收集条件。保留结构不代表新版本机制仍相同。结构完整、忠实复现和实际好用是三个不同问题，分别用数据检查、兼容检查和真实游戏使用判断，避免把一种结果当成另一种证明。
